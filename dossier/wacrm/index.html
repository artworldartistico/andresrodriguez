Contexto y alcance

Qué existía antes y qué problema resolvió esta intervención.

WACRM es una solución CRM open source construida sobre Next.js y Supabase que centraliza conversaciones de WhatsApp, contactos, pipelines comerciales, automatizaciones y agentes de IA. El proyecto base ya existe; el trabajo documentado aquí consiste en llevarlo desde un repositorio clonado hasta un entorno productivo estable y reproducible.

El alcance cubre cuatro frentes: un entorno local containerizado con recarga en caliente para desarrollo, una imagen de producción optimizada y sin secretos horneados, una base de datos gestionada con migraciones versionadas, y un flujo de despliegue continuo donde cada cambio validado en local llega a producción con un git push.

Criterio de trabajo. Ninguna corrección se aplicó a ciegas. Cada fallo se aisló reproduciéndolo primero en local, se formuló una hipótesis, se verificó con una prueba concreta y solo entonces se modificó código o configuración. Ese método es el que explica la sección de incidencias.

Fase 1

Entorno local con Docker

Ejecutar el proyecto de forma aislada y reproducible, sin instalar Node en la máquina y sin chocar con los contenedores ya existentes.

Clonado y verificación del remoto

Con varias cuentas de GitHub configuradas, el primer control es confirmar a qué repositorio apuntan los push antes del primer commit. Docker no interviene aquí: lo determina el remoto de Git y la clave SSH en uso.

bash
git clone <url-del-fork> wacrm
cd wacrm
git remote -v        # confirma cuenta personal vs. cuenta cliente

Elección del tipo de contenedor

El árbol del proyecto (package.json, next.config.ts, src/, supabase/) descarta el patrón nginx:alpine usado para sitios estáticos: una aplicación Next.js necesita runtime Node, dependencias instaladas y variables de entorno. Se define un contenedor Node con mapeo 8085:3000, ya que Next escucha internamente en el 3000.

Operación del contenedor

bash
# levantar / reconstruir
docker compose up -d
docker compose up -d --build

# observar
docker ps
docker compose logs -f wacrm

# operar
docker exec -it wacrm sh
docker compose restart
docker compose down

# puerto alternativo sin tocar el compose
HOST_PORT=8086 docker compose up -d

Aplicación disponible en http://localhost:8085.

Fase 2

Containerización

Una imagen de producción pequeña y segura, y un contenedor de desarrollo con recarga en caliente, ambos desde el mismo Dockerfile.

Dockerfile multi-stage

Tres etapas: dependencias cacheadas hasta que cambie el lockfile, compilación, y un runtime mínimo que solo contiene la salida standalone de Next.js y arranca con un usuario sin privilegios.

Dockerfile
# Etapa 1 — dependencias (caché hasta que cambie package-lock.json)
FROM node:20-alpine AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci

# Etapa 2 — build. Las NEXT_PUBLIC_* se inlinean en el bundle del
# cliente, por lo que deben entrar como build args.
FROM node:20-alpine AS builder
WORKDIR /app
COPY --from=deps /app/node_modules ./node_modules
COPY . .
ARG NEXT_PUBLIC_SUPABASE_URL
ARG NEXT_PUBLIC_SUPABASE_ANON_KEY
ARG NEXT_PUBLIC_SITE_URL
ARG NEXT_PUBLIC_APP_LOCALE=en
ENV NEXT_PUBLIC_SUPABASE_URL=$NEXT_PUBLIC_SUPABASE_URL \
    NEXT_PUBLIC_SUPABASE_ANON_KEY=$NEXT_PUBLIC_SUPABASE_ANON_KEY \
    NEXT_PUBLIC_SITE_URL=$NEXT_PUBLIC_SITE_URL \
    NEXT_PUBLIC_APP_LOCALE=$NEXT_PUBLIC_APP_LOCALE \
    NEXT_TELEMETRY_DISABLED=1
RUN npm run build

# Etapa 3 — runtime mínimo
FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production PORT=3000 HOSTNAME=0.0.0.0
RUN addgroup -S nextjs && adduser -S nextjs -G nextjs
COPY --from=builder --chown=nextjs:nextjs /app/.next/standalone ./
COPY --from=builder --chown=nextjs:nextjs /app/.next/static ./.next/static
COPY --from=builder --chown=nextjs:nextjs /app/public ./public
USER nextjs
EXPOSE 3000
CMD ["node", "server.js"]

Decisiones deliberadas:

  • npm ci en lugar de npm install: instalación reproducible desde el lockfile.
  • Salida standalone: la imagen final no arrastra node_modules completo.
  • Usuario nextjs sin privilegios en el runtime.
  • Solo variables públicas como ARG; ningún secreto queda en una capa de la imagen.

Docker Compose para desarrollo

Compose sobrescribe el CMD de producción con npm run dev, monta el código como volumen para hot reload y preserva los node_modules del contenedor con un volumen anónimo.

docker-compose.yml
services:
  wacrm:
    build:
      context: .
      args:
        NEXT_PUBLIC_SUPABASE_URL: ${NEXT_PUBLIC_SUPABASE_URL}
        NEXT_PUBLIC_SUPABASE_ANON_KEY: ${NEXT_PUBLIC_SUPABASE_ANON_KEY}
        NEXT_PUBLIC_SITE_URL: ${NEXT_PUBLIC_SITE_URL:-}
        NEXT_PUBLIC_APP_LOCALE: ${NEXT_PUBLIC_APP_LOCALE:-en}
    container_name: wacrm
    working_dir: /app
    env_file: [.env]            # secretos solo en runtime
    volumes:
      - .:/app
      - /app/node_modules
    environment:
      NODE_ENV: development
      PORT: 3000
    ports:
      - '${HOST_PORT:-8085}:3000'
    command: npm run dev
    restart: unless-stopped
    healthcheck:
      test: ['CMD','node','-e',"fetch('http://localhost:3000')
        .then((r)=>process.exit(r.ok||r.status<500?0:1))
        .catch(()=>process.exit(1))"]
      interval: 30s
      timeout: 5s
      retries: 3
      start_period: 15s

El healthcheck consulta la aplicación desde dentro del contenedor y acepta cualquier respuesta por debajo de 500, de modo que un 404 de ruta no marque el servicio como caído.

Fase 3

Variables de entorno

Que las claves públicas lleguen al build y las privadas nunca salgan del runtime ni del repositorio. Este fue el punto que más incidencias generó y el que define la seguridad del despliegue.

VariableNaturalezaMomento
NEXT_PUBLIC_SUPABASE_URLPúblicaBuild + runtime
NEXT_PUBLIC_SUPABASE_ANON_KEYPúblicaBuild + runtime
NEXT_PUBLIC_SITE_URLPúblicaBuild + runtime
NEXT_PUBLIC_APP_LOCALEPúblicaBuild + runtime
SUPABASE_SERVICE_ROLE_KEYSecretaSolo runtime
ENCRYPTION_KEYSecretaSolo runtime
META_APP_SECRETSecretaSolo runtime

El prefijo NEXT_PUBLIC_ no es cosmético: Next.js incrusta esas variables en el JavaScript que descarga el navegador. Por eso pueden pasarse como ARG sin riesgo, y por eso una clave privilegiada nunca debe llevar ese prefijo. Las tres secretas se inyectan en ejecución —vía env_file en local y vía panel de variables en producción— y nunca quedan en una capa de la imagen.

En el repositorio, .gitignore excluye todo .env* conservando los ejemplos, y .dockerignore excluye además .git, node_modules, .next, docs y los propios ficheros de Docker para no ensuciar el contexto de build.

Fase 4

Base de datos y migraciones

Llevar el esquema completo —tablas, funciones, triggers y políticas RLS— a un proyecto gestionado de Supabase de forma versionada y repetible.

En lugar de pegar scripts a mano en el editor SQL, se vinculó la CLI de Supabase al proyecto remoto y se aplicaron todas las migraciones del directorio supabase/migrations/ con un solo comando. La conexión se resolvió mediante session pooler, ya que la conexión directa no está disponible en el plan utilizado.

powershell
supabase --version
supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push

Verificación en el Table Editor de Supabase, comprobando la creación de las tablas del dominio: contactos, conversaciones, mensajes, pipelines, automatizaciones y configuración de IA.

Fase 5

Despliegue continuo

Que producción se actualice sola al hacer push, sin que el entorno local pueda romperla y sin comandos manuales de despliegue.

Flujo establecido

flujo
cambio en local  →  docker compose up -d  →  prueba en :8085
       ↓
git add . && git commit -m "..." && git push origin main
       ↓
Railway detecta el commit → build por Dockerfile → deploy → dominio público

Configuración del servicio

  • Servicio conectado al repositorio de GitHub, con acceso restringido a los repositorios seleccionados en lugar de a la cuenta completa.
  • Las siete variables cargadas en el panel del servicio, con NEXT_PUBLIC_SITE_URL apuntando al dominio de producción y no a localhost.
  • Sin mapeo de puertos: la plataforma inyecta su propio PORT y gestiona dominio y TLS. El 8085 es exclusivo del entorno local.

Aislamiento entre entornos. Producción no lee nada de la máquina local: se reconstruye desde el repositorio con sus propias variables. Un contenedor local roto no afecta al servicio desplegado, y como .env está en .gitignore, las credenciales locales nunca viajan en un push.

Alternativas evaluadas

Antes de consolidar la plataforma se compararon cuatro rutas: PaaS gestionado, PaaS autoalojado sobre VPS (Coolify, Dokploy), hosting Node gestionado y VPS manual con PM2 y Nginx. El criterio no fue el precio sino si la plataforma resolvía el fallo de build o solo lo trasladaba: cambiar de proveedor no arregla un error de prerender de Next.js. Se mantuvo el PaaS gestionado por menor carga de mantenimiento, rollback integrado y TLS automático, dejando documentada la ruta de migración a VPS con Docker si el coste por minuto de build lo justifica.

Fase 6

Sincronización con el proyecto original

Incorporar las mejoras del repositorio origen sin perder la configuración propia de ambos entornos.

El fork solo tenía configurado origin. Se añadió el remoto upstream apuntando al repositorio original y se integraron sus commits mediante merge, conservando el historial completo.

bash
git remote add upstream <url-del-repositorio-original>
git fetch upstream
git log --oneline HEAD..upstream/main    # ver qué llega antes de integrar
git merge upstream/main --no-edit

El merge produjo conflictos en los tres archivos de infraestructura: Dockerfile, docker-compose.yml y .dockerignore. La resolución no fue elegir un lado, sino combinar: se adoptó el Dockerfile multi-stage con salida standalone y el healthcheck del upstream, y se conservaron el puerto 8085, el modo desarrollo con volúmenes y el env_file local del lado propio.

bash
git add .dockerignore Dockerfile docker-compose.yml
git commit --no-edit -m "chore: merge upstream/main - resolve Docker config conflicts"
docker compose up -d --build     # validar en local antes de publicar
git push origin main
Fase 7

WhatsApp y agentes de IA

Los dos módulos que dan sentido al producto: el canal de mensajería y la capa conversacional automatizada.

Canal de WhatsApp

Integración con la API oficial de WhatsApp Cloud de Meta. Endpoints expuestos por el build de producción:

EndpointFunción
/api/whatsapp/webhookRecepción de mensajes y eventos de estado desde Meta
/api/whatsapp/sendEnvío de mensajes salientes
/api/whatsapp/configConfiguración y verificación del registro del número
/api/whatsapp/templatesSincronización y envío de plantillas aprobadas
/api/whatsapp/broadcastEnvíos masivos sobre segmentos de contactos
/api/v1/webhooksWebhooks salientes hacia sistemas externos

La firma de los webhooks entrantes se valida con META_APP_SECRET y las credenciales del canal se almacenan cifradas con ENCRYPTION_KEY: por eso ambas se tratan como secretos de runtime. El webhook debe apuntar al dominio público con HTTPS, nunca a localhost.

Agentes de IA: incorporación de un tercer proveedor

El módulo soportaba OpenAI y Anthropic. Se añadió Google Gemini como tercera opción seleccionable, lo que exigió tocar cuatro capas distintas: un buen ejemplo de por qué un cambio aparentemente cosmético no lo es.

  1. Interfaz — nueva opción en el selector de proveedor de la configuración del agente.
  2. Capa de proveedor — integración del SDK de Google en src/lib/ai/providers/ y actualización de los identificadores de modelo por defecto.
  3. Validación — ampliación del esquema Zod de POST /api/ai/config y del tipo TypeScript inferido.
  4. Base de datos — ampliación del check constraint de la columna provider, que rechazaba cualquier valor distinto de los dos originales.
typescript · validación de la API
provider: z.enum(['openai', 'anthropic', 'google'])
sql · constraint en PostgreSQL
ALTER TABLE ai_configs DROP CONSTRAINT IF EXISTS ai_configs_provider_check;
ALTER TABLE ai_configs ADD CONSTRAINT ai_configs_provider_check
  CHECK (provider IN ('openai', 'anthropic', 'google'));

Omitir el último paso produce un fallo al guardar aunque la API valide correctamente: el rechazo ocurre en la base de datos. Validación final en el playground del agente, comprobando prueba de clave, persistencia de la configuración y respuesta del modelo con la personalidad y las reglas de negocio definidas en el system prompt.

Fase 8

Incidencias y resolución

Cinco fallos representativos, con el razonamiento que llevó a cada solución. Esta es la parte que distingue seguir un README de implementar un sistema.

01 El build de producción falla al pre-renderizar /forgot-password
SÍNTOMA
Error: @supabase/ssr: Your project's URL and API key are required to create a Supabase client!, seguido de Export encountered an error on /(auth)/forgot-password/page y salida con código 1. En desarrollo la aplicación funcionaba sin problemas.
DIAGNÓSTICO
Next.js genera estáticamente todas las rutas que considera estáticas durante next build. Esa página instancia el cliente de Supabase, que exige URL y anon key en el momento de la compilación, no en ejecución. Si faltan, la librería lanza excepción y detiene el build entero.
SOLUCIÓN
Garantizar las variables públicas durante el build mediante ARG + ENV en el Dockerfile, y forzar renderizado dinámico en las rutas de autenticación que dependen del contexto de petición.
typescript
export const dynamic = 'force-dynamic';
02 Las variables existen en la plataforma pero llegan vacías al build
SÍNTOMA
Las siete variables estaban correctamente cargadas en el panel y aun así el build seguía fallando por variables ausentes.
DIAGNÓSTICO
En lugar de seguir modificando código a ciegas, se instrumentó el Dockerfile con una sonda que imprime en el log si la variable llega o no. El log devolvió MISSING, lo que probó que el problema no era el valor sino el ciclo de vida de Docker: las variables de servicio se inyectan en runtime, mientras que RUN npm run build ocurre en build time y solo ve lo declarado como ARG.
SOLUCIÓN
Declarar las variables públicas como ARG y elevarlas a ENV antes del paso de compilación, dejando los secretos exclusivamente como variables de ejecución. La sonda se retiró una vez confirmado el diagnóstico.
Dockerfile · sonda de diagnóstico
RUN test -n "$NEXT_PUBLIC_SUPABASE_URL" \
    && echo "SUPABASE_URL: OK" || echo "SUPABASE_URL: MISSING"
03 Bucle 307 → 404 en el entorno local
SÍNTOMA
localhost:8085 redirigía a /login con un 307 y esa ruta devolvía 404, mientras producción funcionaba correctamente. Reiniciar el contenedor no cambiaba nada.
DIAGNÓSTICO
Los logs del contenedor mostraron el par 307/404. La causa estaba en el .env: NEXT_PUBLIC_SITE_URL apuntaba al dominio remoto de producción y sin esquema https://, de modo que el middleware construía redirecciones contra un origen que no coincidía con el host local.
SOLUCIÓN
Fijar NEXT_PUBLIC_SITE_URL=http://localhost:8085, recrear el contenedor para que Compose reinyecte las variables —un restart reutiliza el contenedor y no basta— y validar en ventana de incógnito para evitar la redirección cacheada por el navegador.
04 MISSING_MESSAGE en traducciones tras sincronizar con el upstream
SÍNTOMA
Error de internacionalización al abrir la pantalla de configuración, solo en local; en producción la misma pantalla cargaba bien.
DIAGNÓSTICO
El merge actualizó los archivos de traducción, pero el servidor de desarrollo dentro del contenedor seguía sirviendo la caché previa de .next. Producción no tenía el problema porque compila desde cero en cada deploy. El contraste local/producción fue justamente la pista que apuntó a caché y no a código.
SOLUCIÓN
Eliminar el directorio .next, reiniciar el contenedor para forzar la reindexación y recargar con caché limpia.
05 La base de datos rechaza el nuevo proveedor de IA
SÍNTOMA
Failed to save AI configuration al guardar, pese a que el modelo respondía correctamente en la prueba de clave. Al aplicar la corrección, un segundo error: 42P01: relation "ai_config" does not exist.
DIAGNÓSTICO
Dos capas distintas. La primera, un check constraint en PostgreSQL que solo admitía los dos proveedores originales: el UPDATE se rechazaba en base de datos aunque la validación de la API ya aceptara el nuevo valor. La segunda, un supuesto equivocado sobre el nombre real de la tabla.
SOLUCIÓN
Consultar el esquema real antes de alterarlo y aplicar el ALTER TABLE sobre el nombre verificado, alineando constraint, esquema Zod y tipos de TypeScript.
sql
SELECT table_name FROM information_schema.tables
WHERE table_schema = 'public' AND table_name LIKE '%ai%';
Fase 9

Validación funcional

Criterios de aceptación comprobados en ambos entornos antes de dar la implementación por cerrada.

  • Contenedor en estado Up y healthcheck en healthy
  • Aplicación respondiendo 200 en localhost:8085 con hot reload activo
  • Build de producción sin errores: 51 páginas generadas y TypeScript limpio
  • Autenticación operativa, incluida la recuperación de contraseña que rompía el build
  • Migraciones aplicadas y tablas visibles en el panel de Supabase
  • Despliegue automático disparado por commit, con estado correcto
  • Módulos de CRM accesibles: contactos, conversaciones, pipelines y automatizaciones
  • Endpoints de WhatsApp registrados y webhook alcanzable desde el dominio público
  • Agente de IA guardando configuración y respondiendo con los tres proveedores
